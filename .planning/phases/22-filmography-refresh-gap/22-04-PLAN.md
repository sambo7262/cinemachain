<threat_model>
**Threats considered for Plan 22-04 (deploy + verification):**

1. **Migration applied to wrong database.** Mitigation: the deploy task explicitly instructs
   the user to run `alembic upgrade head` against the NAS Postgres via `docker compose exec`,
   not against a local dev DB. The acceptance criteria require visual confirmation of `\d
   actors` showing the new column on the NAS DB specifically.

2. **Production data corruption from migration.** Mitigation: migration 0019 is purely additive
   (nullable column, no backfill, no destructive change). Even if applied to a misconfigured
   database, the worst case is "column added to a DB that doesn't need it" — trivial to
   `alembic downgrade -1` or `op.drop_column`. Plan 22-01 acceptance criteria explicitly forbid
   any UPDATE/backfill in the migration.

3. **TMDB rate limit blowup during Verification B.** Mitigation: the manual refresh button
   triggers `manual_actor_refresh_job` which uses the SAME sleep-per-actor pattern (0.05s) and
   semaphore as the nightly job. The first run on a fresh deploy is bounded by `top_actors`
   (1500 by default) × 2 TMDB calls per actor with serial sleep ≈ ~10 minutes total. Well
   within TMDB free-tier daily budget. If 429s appear in logs, document in Verification B
   notes and consider a follow-up plan to add 429 backoff to `refresh_top_actors_force`.

4. **User accidentally clicks the button twice during the 10-minute run.** Mitigation: the
   button is disabled while `cacheRunning` is true, and even if React state desyncs, the
   backend `_cache_state.running` guard returns `{running: true}` on the second POST without
   doing any work. Worst case: confusing UX, no extra TMDB load.

5. **Secrets visible in `docker logs` during the verification log tail.** Mitigation: Phase 18
   `ScrubSecretsFilter` + httpx event hooks are installed on the root logger and TMDB client.
   The log lines the user is instructed to grep for (`manual_actor_refresh_job starting`,
   `force-refreshing N actors`, `complete`) contain no key material by construction.
   `scrub_traceback` is invoked for any exception logged inside the refresh path. If a key
   leaks despite this, it's a Phase 18 regression and warrants a separate hardening pass —
   surface to user as a SECURITY note in the SUMMARY, not as a phase 22 verification failure.
</threat_model>
